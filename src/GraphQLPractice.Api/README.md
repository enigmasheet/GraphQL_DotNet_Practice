# GraphQLPractice.Api

A **modular monolith**: Hot Chocolate 16 GraphQL over PostgreSQL (EF Core 10).

## Running

```powershell
dotnet run --project src\GraphQLPractice.Api
```

| Surface | URL |
|---|---|
| GraphQL endpoint + Nitro IDE | `http://localhost:5100/graphql` |
| Nitro on its own path | `http://localhost:5100/graphql/ui` |
| Schema SDL | `http://localhost:5100/graphql/schema` |

The database connection comes from `ConnectionStrings:Postgres` in `appsettings.Development.json`
(the shared `masterTest` instance on port `55432`). See [../../docs/dev-setup.md](../../docs/dev-setup.md).

## Modules

```
Program.cs                 # composition root: registers modules, GraphQL, CORS
Modules/
  IModule.cs               # Register(services)
  ModuleRegistry.cs        # the explicit module list
  ModuleInfo.cs            # [assembly: Module("Types")] + [DataLoaderModule("DataLoaders")]
  Authors/                 # AuthorQueries, AuthorNode, AuthorMutations, AuthorConfiguration,
                           #   DataLoaders/
  Posts/                   # PostQueries, PostNode, PostMutations, PostSubscription,
                           #   BlogPostConfiguration, DataLoaders/
  Comments/                # CommentQueries, CommentNode, CommentMutations, CommentSubscription,
                           #   CommentConfiguration
  Tags/                    # TagQueries, TagMutations, TagConfiguration
Errors/                    # domain exceptions used by [Error(typeof(...))]
Models/                    # shared domain entities (the shared kernel)
Data/                      # AppDbContext + SeedData + Migrations
```

Each module owns its GraphQL types (source-generated by `[QueryType]`/`[MutationType]`/
`[ObjectType<T>]`) and its `IEntityTypeConfiguration<T>` (applied by `AppDbContext`).

## Pagination model

Every list is a Relay connection built with the v16 `[UseConnection]` API:

```csharp
[UseConnection(IncludeTotalCount = true, MaxPageSize = 50)]
[UseFiltering]
[UseSorting]
public static async Task<PageConnection<BlogPost>> GetPostsAsync(
    PagingArguments pagingArgs,
    QueryContext<BlogPost> query,
    AppDbContext db,
    CancellationToken ct)
    => await db.BlogPosts
        .With(query, sort => sort.IfEmpty(s => s.AddAscending(p => p.Id)))
        .ToPageAsync(pagingArgs, ct);
```

Notes:
- `QueryContext<T>` carries the client's selection (projection), `where` and `order` into the
  resolver. It **replaces** `[UseProjection]` — don't combine both on a field (analyzer `HC0099`).
- `.With(query, sort => sort.IfEmpty(...))` supplies a **default ordering**; cursor pagination needs
  a stable key.
- `RequirePagingBoundaries = true` (see `Program.cs`) means every paged field must be given `first`
  or `last` — otherwise `HC0082`.
- Nested resolvers use `[Parent(requires: nameof(T.Id))]` so the key is always projected.

`DataLoaders` are kept only where a field is a single object rather than a page: `BlogPost.author`,
`Comment.author`, `Comment.post`.

## Global object identification

`AddGlobalObjectIdentification()` (in `Program.cs`) turns on the Relay `Node` interface. Every entity
is decorated with `[Node]`, each module's queries expose a `[NodeResolver]` (`ResolvePostAsync`, …), and
entity `id`s are surfaced as global `ID!` values (`QmxvZ1Bvc3Q6MQ==` ⟷ `BlogPost:1`). The legacy
`authorById`/`postById` fields are `[GraphQLDeprecated]` and resolvers are hidden with `[GraphQLIgnore]`
so only `node(id:)`/`nodes(ids:)` appear on `Query`.

## Migrations

```powershell
dotnet ef migrations add <Name> --project src\GraphQLPractice.Api --output-dir Data\Migrations
dotnet ef database update --project src\GraphQLPractice.Api
```

`AppDbContextFactory` supplies the connection string at design time, so the CLI does not boot the web
app.
